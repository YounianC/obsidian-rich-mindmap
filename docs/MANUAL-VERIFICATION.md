# 人工验证清单

分支 `feat/mindmap-plugin`。本清单是 15 个任务 + 复核修复轮次里，实现者和复核者反复写下、又反复追加的"待人工验证"条目的合并版——原始记录散落在 `.superpowers/sdd/2026-09-03-obsidian-mindmap/`（gitignore、即将删除）的 16 份报告与 `progress.md` 里，本文件是它们的唯一存档，随代码一起提交、跟踪。

## 0. 自动化门禁已经覆盖了什么、没覆盖什么

以下四条命令在当前分支全部通过（194 个测试，8 个纯函数文件）：

```bash
npx tsc --noEmit          # 类型检查
npx vitest run            # 单元测试 + 属性测试，194 passed
npm run build             # esbuild 打包，产出 main.js
node scripts/check-purity.mjs   # 纯函数层边界校验（src/model/*.ts 6 个 + view/layout.ts + view/camera.ts，禁止 import obsidian / 引用 DOM）
```

**这四条命令能确认的**：`marks.ts`/`parser.ts`/`serializer.ts`/`tree-ops.ts`/`collapse-state.ts`/`layout.ts`/`camera.ts` 这些纯函数在任意合法输入、以及 fast-check 生成的随机输入下行为正确，包括往返稳定性（`parse(serialize(doc))` 恒等、`serialize(parse(md)) === md` 对规范化文件恒成立）；类型契约自洽；纯函数层没有偷偷 import DOM/obsidian。

**这四条命令确认不了的**：任何需要真实 Obsidian 运行时、真实 DOM 布局、真实指针/键盘事件的行为——也就是 `view.ts`、`src/view/*.ts`（`renderer`、`interaction`、`drag`、`camera` 的事件绑定部分、`toolbar`、`marks-panel`、`popover`、`controls`）里几乎所有代码。这正是本文件存在的原因：设计文档 §9 把纯函数层和视图/DOM 层的验证方式明确分开，后者只能由人在真实 vault 里逐项确认。历史上已经发生过"四项机械验证全绿、但真实渲染出来节点文字是竖排的"这类事故（见下文标记 🔴 的条目），说明机械门禁对布局/渲染是盲的，不是走个形式。

## 1. 环境准备

1. 仓库根目录已有 `test-vault/`（gitignore，不进 git），其中 `.obsidian/plugins/rich-mindmap/` 通过符号链接指向仓库根的 `main.js`/`manifest.json`/`styles.css`，`工作内容.md` 是示例导图文件。若目录或链接缺失，重建：
   ```bash
   npm run build
   mkdir -p test-vault/.obsidian/plugins/rich-mindmap
   ln -sf "$PWD/main.js" test-vault/.obsidian/plugins/rich-mindmap/main.js
   ln -sf "$PWD/manifest.json" test-vault/.obsidian/plugins/rich-mindmap/manifest.json
   ln -sf "$PWD/styles.css" test-vault/.obsidian/plugins/rich-mindmap/styles.css
   ```
2. 每次改代码后需要 `npm run build`（或 `npm run dev` 开 watch）重新生成 `main.js`，符号链接是活的，Obsidian 里手动 reload 插件（设置 → 社区插件 → 关闭再打开「Rich Mindmap」，或 Cmd/Ctrl+P 执行 "Reload app without saving"）即可看到最新代码。
3. 用 Obsidian 打开 `test-vault` 作为 vault，进入设置 → 社区插件，关闭「安全模式」，启用「Rich Mindmap」插件。
4. 建议亮色、暗色两套 Obsidian 主题各跑一遍下面的核心检查（第 2、3、5 节），因为所有颜色都来自 Obsidian CSS 变量，只有真实渲染才能看出对比度问题。

## 2. 最基本的：能打开、能渲染、不损坏文件

在做任何交互测试之前，先确认这三条——如果这里就出问题，后面的测试没有意义。

- [ ] 打开 `工作内容.md`：自动进入思维导图视图（frontmatter 里 `mindmap: true` 生效），画布上的树形结构、层级深度与文件里的缩进列表一致，节点文字里看不到 `(p1)`/`(30%)`/`(flag:red)` 这类标记原文——它们应该已被解析成图形标记。
- [ ] 🔴 **节点文字是正常横排、可正常换行的多字符文本，不是每行一个字的竖排列**（历史真实 bug：`.mm-node` 与 `.mindmap-measure` 都是 `position:absolute` 且父容器无宽度声明，导致收缩到 min-content = 单字宽度；已通过给 `.mm-node` 加 `width: max-content` 修复。这是一个"四项机械门禁全绿、外观完全错误"的真实事故，必须用眼睛看，不能只看测试通过）。
- [ ] 长文本节点（超过约 360px 宽度）会自动换行，不会横向撑破画布，不会与同层其他节点的包围盒重叠。
- [ ] 导图视图标题栏右上角有「切换到源码模式」图标按钮（file-text 图标，悬停有提示）；点击后当前面板切到源码模式，内容与文件一致。先在导图里编辑一个节点、1 秒内立刻点该按钮，切到源码后编辑内容应已在文件里（未保存的编辑由基类卸载文件时落盘）。
- [ ] 命令面板执行「切换思维导图 / 源码视图」，切回源码：内容与原文件逐字一致（frontmatter 其他字段不变、没有多余空行/换行）；再次执行命令能切回导图视图。
- [ ] 关闭标签页再重新打开该文件，不报错；打开开发者控制台（Cmd/Opt/I 或 Ctrl/Shift/I），整个测试过程中不应出现红色异常堆栈。
- [ ] 设置里关闭「带 `mindmap: true` 的文件自动用导图打开」后，重新打开该文件应停留在源码模式；用文件右键菜单「以思维导图打开」仍能手动进入导图视图。
- [ ] 在文件浏览器里右键一个文件夹（含库根目录），菜单里有「新建思维导图」；点击后该文件夹下出现 `未命名思维导图.md`，当前面板直接进入导图视图，画布上只有一个文字为「未命名思维导图」的根节点；按 Tab 能新建子节点并落盘。再执行一次，新文件名应为 `未命名思维导图 1.md`。双击根节点改名后切回源码，H1 行随之变化。
- [ ] 🔴 **先在源码模式里打开任意一篇普通笔记（不带 `mindmap: true`），再到文件浏览器里点一个带 `mindmap: true` 的文件：应直接进入导图视图，而不是停在源码模式**（历史真实 bug：从文件浏览器点开文件时，Obsidian 自己那次 `setViewState` 还在读盘、leaf 处于 `working` 状态，此时触发的 `file-open` 里我们的切换调用被重入守卫静默丢弃；只有目标 leaf 原先是另一张导图时才碰巧成功。已修复为切换后校验 `leaf.view` 类型并短间隔重试，见 `main.ts` 的 `flipToMindmap`）。反过来再验证一次：从一张导图点到另一张导图，同样应进入导图视图。
- [ ] 打开一个**没有一级标题**的、带嵌套列表的文件（例如任务清单、纯 Tab 缩进的笔记）：能正常解析成导图，根节点显示为文件名；**不做任何编辑、直接切回源码模式，`git diff` 应为空**（这对应下面"缩进保留"的核心承诺，也是曾经的真实回归——详见文件安全一节）。

## 3. 视觉与主题（对照设计 spec §7）

- [ ] 根节点：填充圆角矩形样式；一/二级节点：无边框文字 + 底部横线；叶子节点：纯文字 + 细底线。
- [ ] 一级分支按固定色相分配（紫/蓝/青/绿/橙/红/粉），子树颜色继承父分支色相，同一分支下颜色一致。
- [ ] 连线为三次贝塞尔曲线，呈现横向 S 形；线宽从约 3px 随层级递减至约 1.5px。
- [ ] 🔴 **节点下划线与连接曲线是同一条连续描边，节点与入边相接处看不到台阶/断裂**——非根节点的下划线不再是 CSS `border-bottom`，而是入边 SVG 路径末尾追加的一段水平线（见 `src/view/layout.ts` 的 `bezier()`）。在 50%、100%、200% 三档缩放下分别检查（历史真实 bug：`border-bottom` 固定 2px、SVG 描边随深度变细到 1.5px，两者中心线对不齐，深层节点尤其明显，源于截图复核）。
- [ ] 下划线粗细随层级变深而变细，与连线本身的线宽变化一致（两者现在是同一条路径，理论上不可能不一致，但仍需肉眼确认没有因为浏览器渲染细节出现视觉断层）。
- [ ] 字号随层级递减：根 18px、一级 16px、二级 15px、三级及以下 14px（用浏览器开发者工具的元素检查或肉眼比对均可）。
- [ ] 亮色、暗色两套 Obsidian 主题下分别过一遍：文字与背景对比度可读，不出现"看不清"的颜色组合。
- [ ] 节点 hover 时有底色反馈；工具栏/控件按钮有 tooltip 文案。
- [ ] 首次打开文件时画布不出现"先堆叠在一起再突然散开"的布局抖动/闪烁。
- [ ] 打开文件后画布自动"适应窗口"（整棵树完整可见），右上角缩放百分比读数与实际缩放一致。

### 标记图形（对照 spec §3.2 档位表）

- [ ] 优先级圆标：p1 红、p2 橙、p3 黄、p4–p7 灰，圆标内数字清晰不溢出。
- [ ] 进度饼图 7 档：0% 显示时钟图标，1%–24% 为 1/6 扇形，25%–41% 为 2/6 扇形，42%–58% 为半饼，59%–75% 为 4/6 扇形，76%–99% 为 5/6 扇形，100% 显示对勾——用示例文件里的 `30%`（应显示 2/6 档，不是四舍五入到 33%）核对边界取整方向。
- [ ] 旗帜：red/orange/yellow/green/blue/purple/gray 七色旗标颜色与名称对应正确。
- [ ] 🔴 **手写一个不落在七档代表值上的进度，例如 `(60%)`：画布应显示第 4 档（半饼→4/6 之间，按区间 `59–75 → 4档`，即和 4/6 扇形同档），打开标记面板时"4/6"这一档应显示为已选中（高亮），而不是没有任何选项高亮**（历史真实 bug：面板曾用精确数值相等判断高亮，`60 !== 67` 导致没有选项高亮；点击视觉上对应的"67%"选项还会把 `60` 静默改写成 `67`，违反"手写原值必须原样保留"的规则。已修复为按档位量化比较）。
- [ ] 紧接上一条：点击这个已高亮的选项——应该**移除**该节点的进度标记（因为按档位判断它已经"选中"），保存后源文件这一行**不应**出现 `67%`；点击其它档位的选项，应写入该档位的代表值（`0/17/33/50/67/83/100`）。
- [ ] 折叠节点旁的角标正常显示子树节点数；折叠状态目前只靠这个角标区分（节点本身外观不随折叠变化，这是已知且验收确认过可接受的设计，不要当成 bug 报告）。
- [ ] 🔴 **折叠角标文案为 `▸ N`（三角 + 数字），胶囊形，与优先级角标（纯数字圆点）在形状和内容上明显可区分**——用户曾反馈两者"长得一样、分不清"（真实反馈，见截图）；hover 角标应有 tooltip「已折叠 N 个子节点，点击展开」。
- [ ] 单击折叠角标：该节点展开，**不进入编辑态**，且没有连带触发第二次折叠/展开（即没有双重切换）。
- [ ] 在折叠角标上快速双击：**不应**进入编辑态（历史设计意图：角标的 click/dblclick 都会 `stopPropagation`，但角标在第一次 click 后会因为节点展开而从 DOM 上消失，第二次点击落点可能已经不在角标上——如果观察到双击后仍然进入了编辑态，这是一个需要报告的真实时序问题，不要凭代码读一遍就假定它必然正确）。

## 4. 键盘与编辑（对照 spec §6.1）

- [ ] 单击节点：出现选中态描边；点击空白画布：取消选中。
- [ ] `Tab`：为选中节点新增子节点并立即进入编辑态、文字全选。
- [ ] `Enter`（非编辑态）：新增兄弟节点并进入编辑。
- [ ] 🔴 **在已有节点上按 F2/双击进入编辑，敲字后按 Enter 提交：只提交这一个节点的文字，不会额外生成一个空的兄弟节点**（历史真实 bug："Enter 提交"事件被就地编辑的 keydown 处理完、又冒泡到画布级 keydown 处理器，后者误判为"非编辑态回车"又新建了一个兄弟节点并进入编辑，每次提交都会多出一个空节点；Esc 同理还会连带取消选中。已修复：编辑框内的 Enter/Esc 会 `stopPropagation`）。
- [ ] `F2`/双击：进入编辑、文字全选；按 `Esc`：取消编辑、内容还原为原值，**且节点仍保持选中状态**（不应该连带清空选中）。
- [ ] 按 `Tab` 新建子节点后立刻按 `Esc`：不应残留空节点，切到源码模式应看不到多出的一行空 `- `。
- [ ] 编辑一个节点，输入 `(p1) 新任务` 后提交：节点应显示红色"1"圆标、文字为"新任务"；切到源码模式确认对应行写成 `- (p1) 新任务`。
- [ ] 把根节点标题改成 `(p1) 我的项目` 并提交：文字应**原样保留**，包括括号和 `p1` 字样（根节点不解析标记，纯文本处理，不应该出现字符丢失）。
- [ ] `Delete`/`Backspace`：删除选中节点及其整棵子树，选中焦点落到下一个兄弟节点。
- [ ] 方向键：上下移动到同层兄弟、左移到父节点、右移到第一个子节点。
- [ ] `Space`：折叠/展开选中节点，角标数字随子树节点数正确变化。
- [ ] 折叠一个节点后切回源码模式，确认 frontmatter 里 `mindmap-collapsed` 记录了正确的路径；切回导图视图，折叠状态保持。
- [ ] 编辑节点文字期间，用滚轮缩放或拖拽画布：编辑框不应丢失焦点或内容错乱。
- [ ] 编辑到一半（未按 Enter/Esc/失焦提交）直接切换到另一个文件再切回来：已经敲的文字应该已被保存（走的是文件卸载时的 blur 提交路径）。
- [ ] 🔴 **在编辑框内按下 Cmd/Ctrl+Enter 或 Cmd/Ctrl+Escape（Obsidian 全局快捷键常用的修饰键组合）：Obsidian 自己的快捷键应正常触发，不应被编辑框吞掉**（历史真实 bug：修复上面 Enter 误触问题时新加的 `stopPropagation()` 没有像画布级处理器一样加修饰键放行判断，导致编辑期间所有 Cmd/Ctrl+Enter/Escape 快捷键失效；已修复，加了 `metaKey||ctrlKey||altKey` 时提前放行的守卫）。
- [ ] 大约 0.4 秒的防抖保存生效（编辑后不是立即写盘，稍等即写），frontmatter 里除 `mindmap`/`mindmap-collapsed` 外的其他键不受任何影响。
- [ ] 🔴 **进入一个节点的编辑态，粘贴一段很长（几千字符）、夹杂大量 `*`/`**`/`~~` 且大部分不闭合的文本（例如代码片段、数学记号、口语化强调堆砌的文字），提交后 Obsidian 不应冻结/卡死，加粗/斜体/删除线该识别的地方应正确识别、不该识别的地方回退为字面文本**（对应 `src/model/inline.ts` 的 `parseSpan` 记忆化 + `MAX_DEPTH` 深度上限；自动化测试只能验证纯函数本身的时间上限和输出结构，验证不了粘贴这个动作本身、以及 Obsidian 真实渲染进程的观感）。

## 5. 拖拽（对照 spec §6.1"节点拖拽"）

- [ ] 小幅移动（未超过约 4px 阈值）只触发选中，不进入拖拽态。
- [ ] 拖到目标节点中部：出现虚线框指示"设为子节点"；松手后目标节点下新增该子节点。
- [ ] 拖到目标节点上/下边缘：出现横线指示"插入到该节点前/后"（同父内为重排，跨父为改变父节点）。
- [ ] 同一父节点内自上往下拖拽重排一位：节点准确移到目标位置后一位，不多跳一格。
- [ ] 尝试把一个节点拖到它自己的子节点上：应被阻止（不产生环）。
- [ ] 根节点不可被拖动。
- [ ] 拖拽中先把指针移到源节点自身或画布空白处（指示线/虚线框应消失），再移回另一个节点上：指示线/虚线框应**重新出现**，不能一旦隐藏就再也不显示（`drag.ts` 改用 `mm-hidden` 类切换浮层显隐时顺带修掉的问题）。
- [ ] 拖拽悬停在目标节点上时，ghost 圆点应始终可见，不应在指针移动时闪烁（命中测试期间临时隐藏浮层后必须恢复原状）。
- [ ] 缩放到 50% 与 200% 两种画布比例下重复以上几项：拖拽指示线/虚线框应正确跟随缩放后的坐标，不偏移。
- [ ] 完成一次拖拽后约 0.4 秒，文件应写回磁盘，且新位置的缩进层级与画布层级一致。
- [ ] 开始拖拽后把指针移出画布面板（拖进侧边栏或移出窗口边缘）再松开：ghost 圆点和指示线应消失，画布不应卡在"拖拽中"状态；连续做三次这个中断动作，不应有残留元素越积越多。
- [ ] 在节点文字上按下并拖出一段原生文本选中，再开始拖拽节点：拖拽应正常进行，松手后画布上不应残留一段被选中的文字高亮。

## 6. 缩放与平移（对照 spec §6.1 相机控制）

- [ ] 打开文件后整图自动适应窗口，右上角百分比读数正确。
- [ ] `Cmd/Ctrl + 滚轮`缩放：鼠标光标下的那个点在屏幕上应保持不动（缩放围绕光标位置，不产生画面"跳动"）。
- [ ] 普通滚轮：画布平移方向符合直觉（不是反的）。
- [ ] 在空白处按下拖拽：画布平移顺畅，光标变为抓手样式；在节点上按下**不**触发平移（应该走选中/拖拽节点逻辑）。
- [ ] 控件条上的 `+`/`-` 按钮缩放，百分比读数同步更新；「适应窗口」按钮能重新把整图居中铺满。
- [ ] 缩放到最大/最小边界时手感正常，不出现空白画面或视图翻转。
- [ ] 拖拽平移中途，鼠标移出 Obsidian 窗口再移回来（或松开在窗口外）：画布不应"粘住"继续跟随光标——之后的正常单击、拖拽应能立刻恢复正常。
- [ ] 🔴 **同一个标签页里连续切换打开多个不同的思维导图文件（每次都用「以思维导图打开」或自动打开），每次都试一下滚轮缩放力度：缩放/平移的灵敏度不应该一次比一次更快**（历史真实 bug：视图实例在同一 leaf 切换文件时会被复用，若相机事件监听器在每次 `render()` 时重复挂载而未去重，会导致监听器叠加，同一次滚轮触发多次缩放，效果是 `factor^N` 级别的指数放大；已修复为整个视图实例生命周期只挂载一次）。
- [ ] 新建/首次打开一个视图、pane 尺寸尚未完成布局时（例如刚拖出一个新分屏就立刻打开导图文件），确认最终仍能正确"适应窗口"，不会因为初次测量到 0 尺寸而永久停在未缩放状态。

## 8. 文件安全：如何证明文件没有被多改一个字节

这是插件最核心的承诺，**不能靠肉眼比对，必须用工具**。以下五种、且仅有以下五种写回变化是被允许的（来自设计 spec §4.6）：

1. 文件末尾补一个换行（如果原来没有）；
2. 松散列表（列表项之间有空行）被压缩成紧凑列表；
3. `CRLF`（`\r\n`）统一转换为 `LF`（`\n`）；
4. 列表缩进单位遵循文件原有的选择（2 空格/4 空格/Tab 等原样保留）；只有当同一文件里缩进单位**混用**、无法归纳出单一一致单位时，才统一改写为每层 2 空格；
5. 行内标记 token 统一按 **优先级 → 进度 → 旗帜** 的顺序写出。

除此之外任何字节变化都是缺陷，包括但不限于：`*`/`+` 列表标记被改成 `-`、标题行多余空格被抹平、frontmatter 结束围栏 `---` 后的尾随空格被丢弃（这三项都是复核中真实抓到过、后来修复的问题，务必重点复查）。

### 验证步骤（复制可用）

```bash
# 1. 先用 git 记录基线
cd /path/to/test-vault-or-any-git-tracked-copy
git status --porcelain   # 确认工作区干净
git diff --stat          # 应无输出

# 2. 用导图视图打开目标文件，不做任何编辑，直接切回源码模式
#    （或者：什么都不做，只是打开过一次再关闭标签页）

# 3. 回到终端，看 git 怎么说
git diff -- 目标文件.md
```

- 如果 `git diff` 为空：文件逐字节未变，通过。
- 如果 `git diff` 非空：把 diff 内容对照上面五条逐行核对——每一处变化都必须能归类到某一条，且只能是那五条。任何归不进去的变化都是缺陷，需要报告（附上 `git diff` 原文和被打开的文件内容）。

对非 git 场景（例如直接在真实 vault 里测试、不想建 git 仓库），用 `diff`：

```bash
cp 目标文件.md /tmp/before.md
# 用导图视图打开、切走
diff -u /tmp/before.md 目标文件.md
```

### 需要针对性构造的用例

- [ ] 一个用 `*` 做列表标记的文件（`* 节点文字`），打开导图视图后切回源码：`git diff` 应为空（历史上曾被静默改写成 `-`，已修复，`MindNode.bullet` 现在记住每个节点原始的项目符号字符）。`+` 标记同理。
- [ ] 标题行写成 `#   我的导图`（标题前多个空格）或 `# 我的导图   `（标题后有尾随空格）的文件：`git diff` 应为空（曾被抹平，已修复，`MindDoc.headingPrefix`/`headingSuffix` 保留原始空白）。
- [ ] frontmatter 结束围栏写成 `--- `（带尾随空格）的文件：`git diff` 应为空（曾被丢弃，已修复，`MindDoc.frontmatterFenceSuffix` 保留）。
- [ ] 一个全文件 Tab 缩进（Obsidian 设置里「Indent using tabs」默认开启时新建的笔记就是这种）的嵌套列表文件，包括**没有一级标题**的版本（例如纯任务清单）：打开导图视图后切回源码，`git diff` 应为空（这条对应"缩进保留"这项 2026-09-04 的改动，历史上有两次真实回归：一次是无条件把所有缩进改成 2 空格，一次是"没有标题就退化成 2 空格"的过度收紧，均已修复）。
- [ ] 在上面 Tab 缩进的文件里，用导图视图按 `Tab` 新增子节点、按 `Enter` 新增兄弟节点：新写入的行应该也用 Tab 缩进，不应该混入一行 2 空格缩进。
- [ ] 一个 CRLF（`\r\n`）换行的文件：打开导图视图能正常解析（不是空导图——曾经的真实 bug，`.` 不匹配 `\r` 导致整个文件被判定为无列表内容）；切回源码后 `git diff` 应显示换行符从 CRLF 变为 LF，这是**允许的**唯一一处非空 diff（对应第 3 条白名单），除换行符本身外内容不应有其他变化。
- [ ] 一个混用空格与 Tab 缩进（同一文件里，比如有的层级用 2 空格、有的层级用 Tab）的文件：打开导图视图后切回源码，**这次允许**看到缩进被统一改写成 2 空格的 diff（这是第 4 条白名单唯一触发的场景，因为文件本身无法归纳出单一一致的缩进单位）——确认改写只影响缩进空白，不影响每行的可见文字内容。
- [ ] 一个 4 空格缩进的普通文件：打开导图视图切回源码，`git diff` 应为空（缩进原样保留为 4 空格，不应被归一化为 2 空格——这是与上一条相对的正常情形，用来确认"混用才归一化"这条件没有被误判过宽）。
- [ ] 执行「标记为思维导图」命令：确认写入 `mindmap: true`（对没有 frontmatter 的文件会新建一个 frontmatter 块，属预期）；同时确认这条命令会把整个文件的换行符统一转成 LF（对应白名单第 3 条），但正文的可见内容不受影响——如果目标文件本身是 CRLF，`git diff` 会显示全文件换行符变化，这是预期的，不是缺陷。

## 9. 需要人为构造场景的测试（AI 协同 / 并发 / 异常）

以下场景不是打开文件点一点就能测到的，需要专门搭建条件。

### 9.1 外部程序同时编辑文件（AI 协同的核心场景）

在 Obsidian 里打开 `工作内容.md`（或任意导图文件）的导图视图，保持窗口可见，然后在另一个终端窗口执行：

```bash
# 模拟外部 AI 直接改文件
cd /path/to/test-vault
cat >> 工作内容.md <<'EOF'
- 新增的外部节点
EOF
```

- [ ] 画布应在短时间内自动刷新，出现"新增的外部节点"；**当前视口（缩放/平移位置）与选中节点应保持不变**，不应该跳回"适应窗口"。
- [ ] 若刷新前选中了某个节点，刷新后只要该节点在新内容里仍存在，选中状态应该保留。

### 9.2 编辑中途被外部覆盖

1. 在画布里双击进入某节点编辑态，敲几个字但**不提交**（不按 Enter/Esc/不失焦）。
2. 这时用上面的 `cat >>` 命令从外部改动文件。

- [ ] 应弹出 Notice 提示"文件已在外部修改，以磁盘内容为准"一类的提示；画布应显示外部内容，本地未提交的编辑被丢弃（这是设计上允许的降级，不是 bug）。

### 9.3 本地防抖窗口内的外部写入（约 400ms 竞态）

1. 正常编辑一个节点提交（触发 400ms 防抖计时器）。
2. 在提交后的 400ms **窗口内**（手速要快，或者写一个小脚本在编辑后立刻执行），用外部程序改动同一文件。

- [ ] 磁盘上最终内容应该是**外部那份**，不是本地待保存的那份（本地的自动保存不应该覆盖掉外部更新的内容）；应弹出与 9.2 相同的外部修改提示。

### 9.4 拖拽进行中被外部编辑打断（最容易被忽略的一个）

1. 在画布上按住一个节点开始拖拽（出现 ghost 圆点），**不要松手**。
2. 这时另开一个终端，向文件头部或被拖节点之前插入一个新的顶层节点：
   ```bash
   sed -i '' '/^# /a\
   - 外部插入的节点
   ' 工作内容.md
   ```
   （或者直接用编辑器手动在列表最前面插入一行 `- 外部插入的节点`）
3. 松开鼠标完成拖拽。

- [ ] 松手后**不应该有任何节点被移动**，画布应显示外部插入节点之后的最新内容（对应已修复的"拖拽 id 复用"问题：节点 id 是每次解析时按前序遍历重新分配的 `n0/n1/n2…`，外部编辑插入/删除一个节点会导致 id 整体错位，若不处理，拖拽收尾时可能用错位后的 id 移动到完全不是用户拖拽时看到的那个节点上——已修复为外部刷新时主动取消进行中的拖拽）。

### 9.5 分屏 / 同一 leaf 切换文件的状态残留

1. 分屏打开两个 pane，一个显示文件 A，一个显示文件 B；点击 B 所在 pane 的空白处使其成为"最近活动"，但确保命令面板要操作的目标其实是 A。
2. 执行「切换思维导图 / 源码视图」命令或用右键菜单在 A 上操作。

- [ ] 命令应该作用在真正显示 A 的那个 pane 上，不是"最近活动"的 B pane。

3. 同一个 leaf 里，打开导图 A，选中一个节点、打开标记面板不关闭，直接切到同一 leaf 里的导图 B。

- [ ] 面板应消失；B 打开时不应有选中、不应有工具栏、相机应是"适应窗口"而不是延续 A 的缩放位置。

4. 在 A 里开始拖动一个节点、不松手，用键盘快捷键切到同一 leaf 的 B，再松手。

- [ ] B 不应有任何节点被移动，B 的文件内容不变。

5. 反复在同一 leaf 里切换 A/B 十几次后，在最终停留的文件上正常使用方向键/Tab/Enter/F2。

- [ ] 全部应正常响应（这是"编辑状态卡死在旧文件"一类 bug 会暴露的地方）。

### 9.6 解析失败与错误态

1. 用文本编辑器把一个正在被导图视图打开的文件改成明显损坏的格式（例如把 frontmatter 的 `---` 只写一半、或者故意造出一个无法解析的结构）。

- [ ] 画布应显示错误提示卡片和「切换到源码模式」按钮；**文件不会被插件写回或修改**（用 `git diff` 确认改坏后到显示错误期间没有额外的写入）。
- [ ] 在错误卡片上点击、拖动：画布不应发生平移，光标不应变成抓取样式（错误卡片需要带 `mm-no-pan` 标记，历史上曾遗漏）。
- [ ] 点击「切换到源码模式」应能正常回到源码查看/修复原始文本。

### 9.7 插件禁用/重启

- [ ] 在 Obsidian 设置里禁用插件、重启 Obsidian、重新启用插件：不应残留错误的视图状态或控制台异常。

### 9.8 大文件流畅度

- [ ] 构造一个约 200 个节点的较大导图文件（可以用脚本批量生成嵌套列表），验证：拖拽、缩放、编辑操作的响应速度可接受，没有明显卡顿；若被外部程序频繁连续改写（例如 AI 逐行追加），画布不应出现密集的闪烁式重绘（目前对连续多次外部编辑没有做防抖合并，属已知、非阻塞项，感受是否明显需要人工判断）。

## 10. 已知限制（这些不是 bug，不要重新报告）

以下三点是复核阶段**有意**留下不修的行为，记录于设计 spec §4「已知限制」，测试中遇到属预期：

1. **外部写入恰好落在插件读取磁盘内容的窗口期内时，仍可能被本地待触发的 400ms 防抖保存悄悄覆盖**。Obsidian 基类在"读取磁盘内容"和"真正写回"之间存在一个短暂时间窗，如果外部修改恰好落在这个窗口里，防抖计时器到点后会用内存里的旧数据覆盖掉刚落盘的外部修改，且没有任何提示。直接的"修法"（在自定义钩子里无条件取消防抖计时器）比它要修的问题更糟——会导致远比这个窗口期竞态更常见的"用户还没保存的编辑被无提示地扔掉"，所以本轮没有修。触发概率极低，如果真的复现，请记录具体操作时序而不是简单报"bug"。
2. **`requestSave()` 故意从不被调用**，因此 Obsidian 基类的按行三路合并保存路径永远是死代码。这是有意为之：对序列化后的导图 Markdown 做文本级三路合并，效果只会比"外部修改到来时磁盘覆盖本地待存改动"更差。如果发现保存机制没有走三路合并，这是设计如此，不是遗漏。
3. **缩进单位推断在"最浅的更深条目本身跳过一级"时会把跳跃宽度当成一级单位**：例如文件里从 0 级缩进直接跳到两个 Tab 缩进、从未出现过一个 Tab 的层级，`detectIndentUnitString` 会把两个 Tab 当作"一级"的单位。这对**现有内容的往返是安全的**（不丢数据、不改字节），但如果之后在导图视图里对这类文件做结构性编辑、新增更深层级，新增的层级会按这个偏宽的单位换算（上例会产出四个 Tab，而不是读起来更自然的三个 Tab）。测试中如果遇到"新增层级的缩进比预期宽"，先检查文件是否属于这种"跳级"情形，属于此已知限制则不必报告。
4. **折叠状态视觉区分完全依赖节点旁的圆角计数徽标**，折叠节点本身外观（下划线、背景等）与未折叠节点相同，没有专门的高亮样式。这是验收时已确认可接受的设计，不是遗漏的 CSS 规则。
5. 少数 CSS 类名有生成但无专门样式规则（`mm-collapsed`、裸 `mm-flag`/`mm-progress` 外层包装类、`mm-panel-section`、`mm-no-pan`）：均已确认要么是纯行为标记类、要么样式已经由子元素/父级提供，不是遗漏。
