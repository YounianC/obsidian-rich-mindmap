# 有序列表参与层级 — 设计文档

日期：2026-09-11

## 1. 目标

让 `1.` / `1)` 形式的有序列表项与无序列表项、标题一样产生导图节点，并且**完全等同**于无序列表项：可编辑、可拖拽、可加兄弟/子节点、可删除、可打标记。

直接动机是一个真实的用户报告。下面这份文件今天在导图视图里是一个没有任何子节点的空根：

```markdown
# 测试标题

1. 这是1
   1. 这是1.2
   2. 这是1.3
2. 这是2
```

原因是 `parser.ts` 的 `LIST_ITEM_RE = /^([ \t]*)([-*+])[ \t]+(.*)$/` 只认 `-` / `*` / `+`，四行有序列表全部落进根节点的 `continuation`。这是 2026-09-04「采纳 markmap 的层级语义」设计文档第 2 节列出的**非目标**，也写在 `README.zh-CN.md` 的「已知限制」第 1 条里 —— 不是缺陷，是一个当时被明确排除、现在要收回的范围。

## 2. 非目标

- **CommonMark 正统的子项缩进**（子项对齐父项的内容列，`- ` 之下 2 格、`1. ` 之下 3 格）不做。序列化仍是 `unit.repeat(depth)`。
- **有序 ↔ 无序互转**不提供 UI 命令。图上新建的节点按继承规则拿到形态，此后不可改。
- **围栏、表格、图片产生节点**仍不做。围栏状态机一个字不动，围栏内的 `1. x` 仍不产生节点。
- **松散列表的空行**仍然不能保留（模型里没有存放的位置），见 4.3。

## 3. 数据模型

### 3.1 `OrderedForm`

沿用项目既有的「可选字段存在与否即形态」惯例（与 `heading?: HeadingForm` 同构），**不引入 `kind` 字段** —— 少一个可能与事实不一致的状态。

```ts
/** 有序列表项的标记形态。存在即为有序项，不存在即为无序项。 */
export interface OrderedForm {
  /** 文件里的原始序号（1–9 位数字）。逐字保留，serialize 直接写出，
   *  只有 tree-ops 的结构变更才会经 renumber 改写它。 */
  number: number;
  /** CommonMark 允许的两种分隔符，原样保留 */
  delim: "." | ")";
}

export interface MindNode {
  // …现有字段不变
  /** 该节点在文件里用的无序标记字符。**仅在 `ordered === undefined` 时被
   *  serialize 读取**；有序节点上它是解析期填入的占位值（`-`）。 */
  bullet: Bullet;
  /** 存在即为有序列表项。标题节点不带此字段（标题形态优先，见 serializer）。 */
  ordered?: OrderedForm;
}

/** 判别列表项形态的唯一入口。不要散落 `node.ordered !== undefined`。 */
export function isOrdered(
  node: MindNode,
): node is MindNode & { ordered: OrderedForm } {
  return node.ordered !== undefined;
}
```

「有序节点上 `bullet` 是死字段」这件事有现成先例：`HeadingForm.level` 同样是「解析期用于层级归属计算、序列化绝不读它」。约束靠注释与 `isOrdered` 这个唯一判别入口维持。

### 3.2 根节点的 `ordered`

根节点自身没有列表行。它的 `bullet` 现在存的是「文件里第一个列表项用的标记字符」，供 `tree-ops` 给根的新直接子节点挑一个与现有兄弟一致的标记。`ordered` 与之**完全对称**：parser 把文件里第一个列表项的 `OrderedForm` 也回填到根上（该列表项是无序时不写这个字段）。

**已知危险：`isOrdered(root)` 会为真，但根不是有序列表项。** 与 `root.bullet` 今天的性质一模一样。安全性来自 `serialize` 的结构 —— 根节点走 `doc.root.heading.prefix` 那条独立分支写出，永远不进 `serializeNodes` 的标记分支。`types.ts` 与 `parser.ts` 两处都要写明这一点。

## 4. 解析（`parser.ts`）

### 4.1 正则与条目

```ts
/** CommonMark 的有序列表标记：1–9 位数字 + `.` 或 `)`。与 LIST_ITEM_RE 一样
 *  要求标记与文字之间有空白，所以 `1.x`、`2026.` 后直接接字都不是列表项。 */
const ORDERED_ITEM_RE = /^([ \t]*)(\d{1,9})([.)])[ \t]+(.*)$/;
```

抽出一个 `matchItem(line)` 辅助函数，依次试 `LIST_ITEM_RE` 与 `ORDERED_ITEM_RE`（两者的第一个有效字符不可能相同，试的顺序无关紧要），返回

```ts
{ indent: string; bullet: Bullet; ordered: OrderedForm | null; text: string } | null
```

`ItemEntry` 增加 `ordered: OrderedForm | null` 字段，`scanDocument` 的列表项分支改为调 `matchItem`。

### 4.2 深度、块、缩进单位：全部不动

`indentWidth`、`itemBlocks`、`detectIndentUnit`、`detectIndentUnitString`、`buildTree` 的深度计算一行不改。有序条目和无序条目在这些函数眼里完全一样，只是 `depthWidth` 天然更大（`1. ` 宽 3、`- ` 宽 2）。

代价见第 7 节。

### 4.3 松散列表压缩加一条同类守卫

`scanDocument` 里判断「空行后紧跟列表项 → 丢弃空行」的那段（归一化第 2 条），现在的三个条件不变，**再加第四个**：空行之后那一行与前一个条目必须是**同一类**列表项（同为有序或同为无序）。

| 形态 | 今天 | 改造后 | 说明 |
|---|---|---|---|
| `- a` / 空行 / `- b` | 压缩 | 压缩 | 不变 |
| `1. a` / 空行 / `2. b` | 保留 | **压缩** | 新行为，见下 |
| `- a` / 空行 / `1. x` | 保留 | 保留 | 守卫生效 |
| `1. a` / 空行 / `- x` | 保留 | 保留 | 守卫生效 |

第 2 行是**不可避免**的：有序项一旦成为节点，两项之间的空行就没有存放的位置了 —— 这正是归一化第 2 条当初存在的理由，现在它的适用面从「无序列表」扩大到「列表」。

第 3、4 行是这条守卫争取来的。CommonMark 认为跨标记类型是两个不同的列表，压缩它们之间的空行既没有必要，又会在今天逐字节保真的文件上凭空产生差异。守卫让这类文件继续保真。

## 5. 序列化（`serializer.ts`）

`serializeNodes` 的列表项分支改两行：

```ts
// 有序项写出自己的号与分隔符，无序项写出自己的标记字符。两者都是「原样重放
// 文件里的形态」的同一条规则，与标题逐字重放 prefix 同源。
const marker = node.ordered === undefined
  ? node.bullet
  : `${node.ordered.number}${node.ordered.delim}`;
out += `${indentUnit.repeat(listDepth)}${marker} ${composeLine(node)}\n`;
```

缩进表达式、`serializeNote` 的缩进、标题分支全部不动。

## 6. 重编号（`tree-ops.ts`）

### 6.1 规则

序号必须逐节点存下来原样写回，否则「打开不改再切走」就会重写用户的 `1. 1. 1.` 写法，违反 AGENTS.md 第 2 条。但用户在图上做结构变更时，受影响的那一段兄弟要重新排号。

新增纯函数：

```ts
/**
 * 结构变更后重排有序兄弟的序号。
 *
 * 「段」= children 里极大的一串连续、**同 delim** 的有序节点。delim 不同在
 * CommonMark 里就是两个列表，跨 delim 连号是错的。
 *
 * 每一段的起始号取 `prev` 里**同序号那一段**的段首号；`prev` 里没有对应段
 * （新长出来的段）时取 1。段内其余节点依次 +1。delim 各自保留不动。
 */
function renumber(
  prev: readonly MindNode[],
  next: readonly MindNode[],
): MindNode[];
```

两个参数（变更前/变更后的同一个父节点的 children）让这个函数是纯的、好测的，且四个 op 都能就地拿到两份数组。

### 6.2 规则在各场景下的结果

| 场景 | prev | next | 结果 |
|---|---|---|---|
| `1,2,3` 在 a 后插入 new | `[[1,2,3]]` | `[[a,new,b,c]]` | `1,2,3,4` |
| `3,4,5` 删掉段首 a | `[[3,4,5]]` | `[[b,c]]` | `3,4` |
| `5. e` 拖到 `1,2` 段首 | `[[1,2]]` | `[[e,a,b]]` | `1,2,3` |
| 给无子节点的有序父加子 | `[]` | `[[new]]` | `1` |
| 无序节点插进 `1,2,3` 中间 | `[[1,2,3]]` | `[[a],[b,c]]` | `1` / `1,2` |
| `1.` 段后接 `5)` 段，前段插一个 | `[[1,2],[5,6]]` | `[[a,new,b],[c,d]]` | `1,2,3` / `5,6` |

倒数第二行是刻意的：无序节点把有序段一分为二，第二段在 CommonMark 里就是一个新列表，从 1 开始重新计数是正确的。

### 6.3 调用点

只对 `children` **真的变了**的那个父节点调用：

- `addChild` —— 目标父节点，一次
- `addSibling` —— 参照兄弟的父节点，一次
- `removeNode` —— 被删节点的父节点，一次
- `moveNode` —— detach 阶段对源父一次，insert 阶段对目标父一次

四处都在现有的 `mapTree` 回调内部，回调里 `node.children` 就是 `prev`，新构造的数组就是 `next`。

**源父与目标父相同时** detach 与 insert 会各跑一次，第二次的 `prev` 是第一次的输出。已验证结果正确：`1,2,3` 里把 c 移到下标 0，detach 得 `a=1,b=2`，insert 得 `c=1,a=2,b=3`。

**关键性质：打开不改再切走时一个 tree-ops 函数都不会被调用，所以什么都不会重编号。** 归一化第 2 条不受影响。

### 6.4 新节点的标记形态继承

沿用现有规则，只是从「继承 `bullet`」扩成「继承标记形态」：

- `addChild(parentId)` —— 取父节点的形态。父节点是有序的，新子节点也是有序的，初始号给 `1`（它要么独自成段 → 起始号就是 1，要么接在既有段尾 → 号由 `renumber` 按段首重算）。
- `addSibling(siblingId)` —— 取参照兄弟的形态，有序时**连号一起复制**（`{ ...target.ordered }`）。插入位置恒为 `index + 1`，所以新节点永远不会成为段首，复制来的号只是个会被 `renumber` 立刻覆盖的合法初值。
- `addSibling` 参照的是标题时仍产出同级标题，不带 `ordered`。
- `moveNode` —— 被移动的节点**保留自己的形态**。无序节点掉进有序段里就把那段一分为二（6.2 倒数第二行），不静默改写用户的标记。

## 7. 已知代价

**有序与无序在同一个列表块里混排、缩进宽度不一致时，触发归一化第 4 条兜底成每层 2 空格。**

```markdown
- a
  - b
1. c
   1. d
```

这四行今天同属一个列表块吗？不 —— 今天后两行是 `b` 的 continuation，逐字保留。改造后四行都是列表项条目，块内缩进出现 2 和 3 两种宽度，`detectIndentUnitString` 归纳不出单一单位，退回两空格兜底，`   1. d` 被改写成 `  1. d`。

这落在 AGENTS.md 归一化第 4 条的措辞里（「某个列表块**内部**混用、无法归纳出单一单位」），**不是第六条归一化**，但它是一个新的触发面，必须写进 AGENTS.md 第 4 条与 README 两份的「写回归一化」一节。

不受影响的形态：纯有序列表（本设计的直接动机）、纯无序列表、以及有序无序混排但缩进宽度一致的文件。

被评估后否决的两个替代方案：按父节点标记宽度算缩进（CommonMark 正统，但会重写大量「有序列表下用 2 空格」的现有文件，是一条全新的归一化）；缩进单位按块存而不是按标题存（保真度最高，但要改 `HeadingForm.indentUnit` 的继承链，回归面最宽）。

## 10. 自动化测不到什么

本次改动全部落在 `src/model/**`（纯函数层），`src/view/**` 与 `styles.css` 一行不改，所以**没有**需要人在真实 Obsidian 里确认的渲染或交互行为。

但仍有两项要人工验证，因为它们跨越了纯函数层的边界：

1. 用真实 vault 打开一份有序列表笔记，确认节点出现在图上、可编辑、可拖拽；插入/删除节点后切回源码模式，确认序号符合 6.1。
2. 打开一份既有的、含有序列表的笔记，什么都不改再切走，`git diff` 必须为空（除非它命中第 7 节的混排异宽形态）。

两项都要加进 `docs/MANUAL-VERIFICATION.md`。实现报告里不得声称视觉或交互行为正确。
